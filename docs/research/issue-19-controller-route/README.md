# Issue #19 — controller, Type-C/PD, firmware and prototype access route

Status: `BLOCKED` for an integrated schematic/layout; research complete as of 2026-09-01.

## Decision-safe result

There is a credible, manufacturer-operated route to obtain the required material, but no public evidence establishes that this project may receive or redistribute the current Intel JHL9440 reference package, NVM image, programming/recovery procedure, or a complete two-host/one-dock implementation. Therefore issue #19 **cannot positively close** yet.

The evidence supports only these narrower propositions:

- Intel lists JHL9440 as a launched, quad-port TB4 accessory controller, while its public page currently shows zero retailers. That page does **not** specify upstream topology, pinout, NVM, firmware, reset sequence, supported mux/PD/power parts, or a purchasing route.
- Infineon's public CCG5 material documents an older dual-upstream dock application built around CYPD5235 and separately documents a dual-downstream dock application built around CYPD5236. The former is useful component/application evidence; neither diagram is evidence for a JHL9440 two-host selector or for the dock-facing domain in this project.
- Infineon exposes a virtual Thunderbolt reference design, but the BOM, schematics, design files and related material require product registration/contact-sales access. Infineon’s own support material ties the Thunderbolt Device Configuration utility to the party that released the controller NVM.

No schematic is proposed here. In particular, **do not infer a two-upstream KVM topology from JHL9440's “Quad” port count or from the CCG5 dual-port drawings.**

Intel publicly lists PCIe Gen4 x4 and DP2.1 tunnel/re-drive capabilities. | Intel page currently displays **0 Retailers**. | Newer launch timing and “Quad” do not prove it supersedes JHL8440 for this product, is sourceable in prototype quantity, or supports a selected two-upstream front end. `NOT FREEZABLE`. |

Both product pages remain public, launched listings rather than discontinuance notices; neither proves current design-in support. The public pages also do not define what “Quad” means electrically or topologically for this project. **Issue #19 therefore needs an explicit Intel question naming both JHL8440 and JHL9440**: which (if either) is the current supported controller/reference route for an externally powered accessory with a selected two-upstream front end and one downstream dock port, and what prototype sourcing, NVM, programming/recovery and redistribution terms apply. Until Intel answers in writing, neither controller may be selected, frozen, sourced or used to reconcile the repository’s historical JHL8440 precedent with its JHL9440 candidate route.

Submit the [Thunderbolt peripheral developer application](https://www.thunderbolttechnology.net/developer-application) for the bounded Prototype-A product: externally powered accessory, two hosts selected one at a time, one downstream dock port, no unsupported claim of continuous dual attachment.
2. Complete the required Intel legal/organization route (Developer Portal and, if directed, RDC/Partner Alliance/CNDA). Ask Intel’s PM to compare **JHL8440 and JHL9440 explicitly**, then give a written answer covering: current supported controller/OPN and prototype quantity source; reference-design revision; explicitly supported port topology; mux/PD/power/clock/NVM parts; board/stack-up/layout constraints; production and prototype firmware/NVM; programming, recovery, version-readback and rollback; bring-up sequence; interoperability/certification path; and redistribution/open-source boundary for each artifact.

5. Reconcile the CCG5 role by explicit written confirmation. The public CYPD5235 application is dock/upstream and public CYPD5236 material is dock/downstream; the project must not select either for the dock port or a two-host switch without the accepted reference package.
6. After written approval, obtain only traceable, authorized prototype parts. For JHL9440, use the Intel-directed channel. For CYPD5235, obtain a written quote/availability and exact OPN/packaging from Infineon or a named authorized distributor; require declared programming state and lot traceability. Do not use broker stock as the evidence route.
7. Before schematic/layout starts, place only non-confidential metadata in the repository: document title, revision/date, access restriction, entitlement owner, artifact hash if contractually permitted, and a requirements-to-reference checklist. Keep confidential schematic, NVM, programming package and firmware outside the repository unless written licenses allow their inclusion.

## Minimum evidence required to close issue #19 positively

All of the following must exist and be independently reviewed:

- written Intel authorization naming the current controller, permitted topology and prototype sourcing route;
- current reference collateral naming or explicitly accepting the PD controller(s), mux, power/protection, clocks, SPI/NVM and the three port-domain roles;
- a legally reproducible firmware/NVM path with exact tool, programming, recovery, readback and rollback evidence;
- written redistribution classification for every vendor artifact, with the public repository containing no restricted content;
- traceable prototype-quantity availability for the controller and companion PD parts; and
- an accepted reference-derived answer for downstream CC/PD/VBUS/VCONN ownership.

Until then, the factual status is `BLOCKED`: controller and CCG5 *families* are evidenced, but the integrated KVM route remains unapproved and non-reproducible.
