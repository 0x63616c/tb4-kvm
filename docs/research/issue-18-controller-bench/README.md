# Issue #18 — PD-free controller/UI bench plan

Status: `PROPOSED` (bench-only proof; not electrical-safety, production-readiness, USB-C/PD, high-speed, or product evidence)

This plan exercises the low-speed control plane from issue #18: one onboard button, an optional request-only remote button/pod, a small display, minimal LEDs, debounce/bounce handling, watchdog reset, brownout/power-loss behavior, and serial event logs. It intentionally excludes every USB-C receptacle, CC/PD/VBUS/VCONN net, Thunderbolt/router/mux net, high-speed signal, dock, target KVM laptop, charger, and valuable equipment. A USB cable may connect to a dedicated development computer only while programming or collecting logs from the isolated dev board; it must never connect to a target KVM laptop, dock, DUT, or product power domain, and it must be disconnected before direct-VSYS testing.

**Power rule:** never apply USB power and direct VSYS bench-supply power simultaneously unless a documented, reviewed diode/FET OR-ing circuit is installed. A beginner-safe sequence is: (1) program and inspect the board over USB; (2) disconnect USB at both ends; (3) verify USB VBUS is absent with a DMM; (4) set a current-limited 3.3 V supply; (5) connect only VSYS and GND; and (6) run the brownout/power-loss tests. Do not assume a USB cable is data-only: back-power through USB VBUS, GPIO, display, UART, or another attached instrument can defeat the supply isolation and corrupt the test. Stop if any unexpected voltage appears on the disconnected USB connector or VSYS.

## Recommended route

Use a **Raspberry Pi Pico 2, order code SC1631** (or SC1632 with headers) on a solderless breadboard, powered from a current-limited 3.3 V bench supply through VSYS only after verifying the board power configuration. Raspberry Pi’s current datasheet identifies the order codes and documents 1.8–5.5 V VSYS input, 3.3 V GPIO, 26 multifunction GPIOs, and 4 MB flash; the SDK documents GPIO and watchdog APIs. [Pico 2 datasheet](https://datasheets.raspberrypi.com/pico/pico-2-datasheet.pdf), [Pico documentation](https://www.raspberrypi.com/documentation/microcontrollers/raspberry-pi-pico.html), [Pico SDK hardware API](https://www.raspberrypi.com/documentation/pico-sdk/hardware.html).

Why this route: it is a small, documented 3.3 V board with enough GPIO for button/display/LED/remote input, UART logging, a watchdog and ADC power observation without involving Type-C power circuitry. This is a recommendation for a disposable bench, not a production-controller selection. Disable or ignore wireless; the Pico 2 (not Pico 2 W) is the bounded choice.

## Wiring boundary

Use a separate breadboard area labelled `LOW-SPEED BENCH — NO USB-C/PD/VBUS/TB`. Keep all wiring at logic level and under the dev-board’s documented GPIO limits. Never connect the bench ground, pins, or supply to a dock, laptop, Type-C cable, KVM board, router, mux, VBUS rail, or any other energized product.

Suggested Pico 2 logical allocation (GPIO numbers are bench assignments, not a PCB pinout):

| Function                      |                     Pico 2 GPIO | Bench connection                                                                                                                                                                                                                                                                                                                                                            |
| ----------------------------- | ------------------------------: | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Onboard button                | GP2 input with internal pull-up | Momentary switch to local GND; add optional 1 kΩ series resistor at the pin                                                                                                                                                                                                                                                                                                 |
| Request-only pod input        |    GP3 input, normally inactive | Short isolated cable from a second momentary switch; series resistor at MCU entry, local pull-up, no power returned to pod                                                                                                                                                                                                                                                  |
| Display I²C SDA/SCL           |                         GP4/GP5 | Small 3.3 V I²C OLED/LCD module only; verify module current and pull-ups before powering                                                                                                                                                                                                                                                                                    |
| Minimal status LEDs           |            GP6/GP7 through 1 kΩ | Red/green LEDs to indicate request/latched-fault only; do not represent PD or link status                                                                                                                                                                                                                                                                                   |
| Serial event log              |                   UART0 GP0/GP1 | 3.3 V USB-UART adapter only, common ground; verify adapter voltage before connection                                                                                                                                                                                                                                                                                        |
| Power observation             |                        ADC GP26 | Proposed external VSYS divider: 100 kΩ top from VSYS to GP26 and 100 kΩ bottom from GP26 to GND, with 100 nF at GP26; at VSYS max 5.5 V and 1% worst-case values (bottom high 101 kΩ, top low 99 kΩ), VGP26 ≤ 5.5 × 101/(99+101) = 2.78 V, below the documented 3.3 V ADC input limit. Sample slowly and record resistor tolerance/capacitor. Never exceed ADC input range. |
| Watchdog/brownout test marker |                      GP8 output | Scope/logic-analyzer probe only; no external actuator                                                                                                                                                                                                                                                                                                                       |

The Pico 2 also exposes a built-in VSYS monitor on ADC3/GP29 (the board’s divided VSYS monitor). GP29 is useful for observing board VSYS, but GP26’s explicit divider is retained so the external measurement path, source impedance, filtering, and injected brownout waveform are reproducible. The divider is a proposed bench instrument input, not a production power monitor; validate calibration against a DMM.

The remote pod is request-only: it may assert a button request and receive no control authority, power-path enable, VBUS, CC, PD, router, or high-speed signal. For an exposed/longer cable, do not use the raw GPIO arrangement above without a reviewed interface. At minimum for this bench, use a short cable, series current-limiting resistors at both ends, a local 3.3 V rail with resettable/current-limited supply, and a low-capacitance ESD/TVS device selected for 3.3 V logic. Treat these as proposed bench protections, not a production interface design; validate leakage, clamping, edge rate and fault current before any longer cable or external access.

Inject bounce only on the isolated button input: use a switch, pushbutton jig, or a 0–3.3 V signal source through at least 10 kΩ and a clamp-reviewed entry. Do not inject negative voltage, over-rail voltage, or energy from a powered product. The firmware must log raw edges and accepted debounced events separately.

## Equipment and BOM categories

Required categories: Pico 2 with headers, solderless breadboard, 3.3 V current-limited bench supply, momentary switches, 1 kΩ/10 kΩ resistors, 3.3 V-compatible small I²C display, two low-current LEDs, low-capacitance 3.3 V ESD protection for the optional cable, USB-UART adapter confirmed 3.3 V logic, short insulated jumper cable, and labeled test leads. Useful: oscilloscope or logic analyzer, DMM, programmable supply/current limit, function generator with 0–3.3 V output, and reset/power-interruption switch. No USB-C/PD analyzer, dock, host laptop, or high-speed instrument is needed or permitted for this bench.

Do not copy a volatile price or stock claim into this record. Confirm the exact board variant and electrical limits at acquisition time through the manufacturer source.

## Assembly sequence

1. Mark the bench and inspect the dev board for headers, damage, and variant identity; record board order code and software/tool versions.
2. Set the supply current limit conservatively, verify 3.3 V with a DMM, and connect only the dev-board power input documented by its datasheet. Confirm reset behavior before adding peripherals.
3. Add the local button, then serial logger. Prove boot, reset-cause logging, all control outputs inactive, and no unexpected pin drive.
4. Add display and LEDs through resistors. Keep labels diagnostic-only (`REQUEST`, `FAULT`, `BOOT`), never `READY`, `PD`, `USB4`, or `40 Gb/s`.
5. Add the remote request line last, with series resistance and the proposed entry protection. Test disconnected, shorted-to-ground, and cable-touch conditions at current limit.
6. Add controlled bounce injection and power interruption at the supply, not at a host or product rail. Capture raw serial logs and scope traces.

## Test matrix and acceptance evidence

| ID  | Test                             | Expected bench evidence                                                                                     |
| --- | -------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| B1  | Cold boot and reset              | Outputs inactive until initialization; boot/reset cause and firmware revision logged                        |
| B2  | Local button clean press/release | One accepted event per press; raw edge count retained                                                       |
| B3  | Synthetic bounce burst           | No duplicate accepted events; debounce interval and rejected edges logged                                   |
| B4  | Long press/repeat                | Explicit long-press policy; no accidental repeated request                                                  |
| B5  | Remote request connected         | Request-only event logged; no output gains authority                                                        |
| B6  | Remote disconnected/open         | No runaway toggling; local control remains deterministic                                                    |
| B7  | Remote short-to-ground           | Input fault/held state is bounded; current remains within the bench limit                                   |
| B8  | Watchdog starvation              | Hardware reset occurs; reset cause and last persisted event are logged                                      |
| B9  | Controlled brownout ramp         | BOR/reset behavior, output state during and after ramp, and reset cause are captured; no safe-product claim |
| B10 | Power loss and restore           | Outputs return to defined inactive defaults; event continuity is labeled volatile/persistent accurately     |
| B11 | Display unplugged/I²C fault      | Control loop continues or enters a declared UI fault; no false status claim                                 |
| B12 | Serial logger unplugged          | Controller behavior remains bounded; loss of logs is visible as an evidence limitation                      |
| B13 | LED-minimal mode                 | Only permitted diagnostic LEDs active; display text and logs remain authoritative                           |

Acceptance means the exact bench firmware passes this matrix with raw serial logs, supply waveform/current notes, reset-cause records, and a wiring/board photo. It does not prove a production state machine, PD behavior, VBUS isolation, Type-C compliance, EMI, cable safety, or compatibility.

## Remaining blockers and unproven claims

The exact controller/reference route, production power architecture, watchdog policy, brownout thresholds, remote-cable interface, display electrical limits, and fault persistence remain design inputs for the later integrated board. This bench can prove software-facing low-speed behavior and reveal reset/logging defects; it cannot prove electrical safety or that any vendor-specific PD/router sequence is correct. Keep the result `PROPOSED` until an independent review of the exact firmware, wiring, test logs, and protections is recorded.

Every referenced artifact—including firmware, wiring photos, power-isolation/VBUS observations, each B-case log/trace, and independent-review evidence—is an object with a repo-relative path and SHA-256, not an unverified filename. For `COMPLETED`, the validator resolves every path inside the repository, rejects absolute paths and traversal (including symlinks escaping the repository), requires a regular file, recomputes its SHA-256, and compares it with the record. Each B1–B13 artifact must declare its owning `caseId`, and a case artifact path cannot be reused for another case; this prevents one generic log from masquerading as evidence for every test. The DRAFT is allowed to contain placeholders but can never be accepted or reviewed; a `PASS` in the DRAFT is only a planned placeholder, not a completed result. A `COMPLETED` record requires the exact board order code and serial/local ID, 40-hex firmware commit plus a firmware artifact whose hash matches `firmwareHash`, wiring revision/photos, non-placeholder tool versions and supply description, current-limited supply and USB isolation evidence, all B1–B13 results as `PASS`, hashed raw artifacts, and independent review. Its explicit false boundary fields prevent the record from being mistaken for USB-C/PD/VBUS/Thunderbolt/high-speed/product validation.
